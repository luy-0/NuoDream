# Jev 双故事候选与用户二选一｜迭代规格

状态：设计稿，供 pi 实现、Codex 验收。分支：`feat/jev-two-story-choice`。

## 目标与边界

用户完成问惑后，八面继续旋转；候选返回后停出两张傩面，让用户选择一场，再进入现有的单面确认、入戏、幻梦与得面流程。Jev 只为八场已注册的固定故事排序，不创作故事、面具、签解或展示文案。用户选择才是最终 `cardId`；选择前不得创建已匹配的 `DreamSession`、跳转剧情或预载某一场的完整剧情。

保留现有八场故事、面具资产和结果页。保留已有 `POST /api/dream/match` 的单故事契约，新增候选接口供正式请面页使用，避免影响其他调用者。

## 内容与判断

在 `src/domain/get-face/` 维护唯一的八故事匹配画像表：每项含稳定选项名、已注册 `cardId`、一条描述用户困境的 `criteria` 字符串，以及一条给用户看的非剧透选择文案。画像依据 `content/dream-cards/` 的当前故事内核人工编写；不将长梗概或全部关键词直接发送给 Jev，也不写相邻故事排除条款。八项应保持相近长度与相同语法，更新故事时同步审阅画像。

首版 `Choice` 的 `instructions` 每轮都只问同一句：“哪一种困境最能解释用户当前的主要阻碍？”`state` 只含修剪后的 `wish`，不包含姓名、会话 ID、故事全文或面具素材。首次调用返回一个首选和八项概率；若最高概率小于 `1`，服务端直接取前两项。若某一选项概率为 `1`，不能靠剩余项的零概率平分顺序决定第二项：由服务端代码将该首项从 `criteria` 剔除，对其余七项再发起一次 `Choice`，以第二轮得分最高项作为第二候选。二轮判定规则、概率判断和选项移除都只存在于代码，不放进 `instructions` 或 `state`；不新增相邻故事边界规则。每轮的 `choice` 必须属于该轮选项，且不得与得分最高项矛盾；第二次也必须严格校验响应，失败时按统一降级路径处理。两个候选必须不同且已注册；概率平分时按固定画像顺序，保证可复现。

首版 `criteria` 与用户可见文案如下。选项名对模型可见，名称本身必须有意义；用户可见文案用于选择卡，不作为第二套匹配规则。

| 选项名 | `criteria`：用户所处的具体困境 | 二选一展示文案 |
| --- | --- | --- |
| 开路｜渡山记 | 面对必须尝试的新事，因没有现成路径或成功保证而迟迟不敢开始。 | 没有现成的路，我还愿意先走一步吗？ |
| 承愿｜一梭花 | 清楚自己真心想做什么，却受钱、工具、时间或其他条件限制，怀疑能否继续。 | 条件还不齐，我能怎样守住所愿？ |
| 聚焦｜第九坛 | 同时追逐多个目标，心力分散，难以决定此刻该把力量放在哪里。 | 想做的事太多，我该先守哪一件？ |
| 守住尺度｜归正记 | 他人的评价和要求不断牵动自己的判断，逐渐失去原本想做什么的把握。 | 听过许多声音后，我怎样找回自己的尺度？ |
| 整合身份｜合页记 | 同时承担多种真实身份和对人的承诺，处处回应却不断失约，感到自己被撕成几份。 | 面对这么多身份，我该怎样安排此刻的自己？ |
| 结束余波｜余火记 | 事情已经结束或补救已经完成，愧疚、反复回想或自我惩罚仍占据现在的生活。 | 记住过去以后，我能让今天继续吗？ |
| 开口求助｜一信渡水 | 需要帮助、回应或理解，却因怕丢脸、怕麻烦别人或怕被拒绝而难以开口。 | 有些话难以说出，我愿意试着开口吗？ |
| 重启生活｜荒年开火 | 重大失去使原有生活崩塌，因想不明白生活的意义而连日常的事也难以继续。 | 答案还没来，我能先把生活接起来吗？ |

`Choice` 一定会选择一个选项，第二高也不保证适配；首版不以 `confidence` 或未经校准的概率阈值宣称匹配正确。二选一界面提供“都不贴近，重新描述”返回问惑。正式发布前，用人工标注样本检查前两项的覆盖与第二项质量；若后者不达标，调整画像或重新设计候选策略，不靠事后修改模型结果掩盖问题。

## OpenRouter 服务端契约

- 服务端通过 `POST https://openrouter.ai/api/alpha/decisions` 调用，模型固定为 `typesafe/jev-1.14`；读取用户已在 Vercel 生产环境配置的精确变量名 `openrouter_jev_key`，不把密钥传到浏览器。使用原生 `fetch` 与显式响应校验即可，无需为单一调用引入 SDK。本地临时密钥只放在被 Git 忽略的 `.env.local` 中。
- 新增 `POST /api/dream/candidates`，请求沿用现有 `wish` 的 2–280 字校验；响应为版本化的 `{ status: "candidates", candidates: [cardId, cardId], provider }`，可附内部可审计的 `promptVersion`。接口绝不返回模型生成的自由文本，也不接收客户端提交的故事卡内容。
- 校验 OpenRouter HTTP 状态、响应结构、每次参与选项概率的有限数值、唯一候选和注册表归属；设置覆盖一至两次调用的明确总超时。缺少密钥、上游超时/错误或异常响应时，由服务端的本地规则给出**稳定的两个不同候选**，并在 `provider` 中标明降级。本地规则若找不到两个有词命中的候选，返回 `{ status: "needs_detail" }`，让用户改写问题；不得沿用现有前三名 50/30/20 随机抽取，也不得把降级分数伪装成模型概率。
- 浏览器到应用接口失败时，停留在可重试的选择准备状态，允许返回修改问题；不静默生成未校验的 `cardId`。日志只记录模型版本、提示词版本、耗时、状态、候选 ID 与降级原因；不记录原始愿望或姓名。

## 前端流程与状态

状态机变为 `name → wish → matching（八面旋转）→ choosing（两面供选择）→ mask（选定单面）→ wearing → complete`。`matching` 保留现有最短展示时长；收到两个候选后，六面退场，两面停在前景。选择卡展示面具缩略图、角色名和一条由本地画像提供的困境文案；点击其中一项后才进入现有单面揭示及“入戏”。界面文案说明这是两种可选择的照面方式，不显示概率、排名或“诊断”语气。

请面会话只持久化两个候选 `cardId` 与用户最终所选 `cardId`，刷新后仍能回到选择界面；旧版已在 `mask` 或 `complete` 的会话可继续，旧版 `matching` 会话回到可重新提交的问惑状态。`DreamSession` 在用户选择后创建，保留下游需要的单一 `match.cardId`，并用版本化的“用户从候选中选择”元数据记录候选来源；兼容读取旧版单故事会话。新元数据不沿用旧 `confidence` 字段，以免把模型概率误写成用户选择的置信度。只预载所选故事的第一幕和后续资源，不预载两场完整故事。返回修改问题时清空旧候选，避免旧结果污染新愿望。

移动端两张候选卡保持可读、可点，键盘可选择；尊重 reduced motion。选择阶段禁止出现单面“入戏”按钮，选择后才出现。候选展示与选中结果必须使用同一 `cardId → 面具` 映射，并通过测试证明八场注册表、画像表和面具映射一致。

## 交付顺序与验收

1. **pi：画像与契约。** 落盘八项 `criteria` 和用户可见文案；实现新响应 schema、OpenRouter 服务端调用及稳定降级。先用 mock 响应验证字段、异常、超时和两个唯一合法 ID。
2. **pi：状态与界面。** 加入 `choosing`、持久化与旧会话迁移；在旋转后展示两面，用户选择后才创建单故事会话、预载并进入现有后续链路。覆盖返回修改、刷新、重复点击、慢请求、`needs_detail` 与请求失败。
3. **pi：评估与视觉自检。** 提供经人审阅的中文样本，包含八场典型输入、相近主题、含糊输入和八场均不贴切的输入；记录前二覆盖、第二候选适配、不同选项顺序下的稳定性和实际耗时。用真实 OpenRouter 调用验证中文质量，但不得上传真实用户困惑作为测试数据。
4. **Codex：监督验收。** 审查画像与故事内核的一致性、端到端状态转移、无密钥泄露与无愿望日志；运行项目 lint、typecheck、相关测试、内容校验、构建，并检查移动端及 reduced motion 体验。真实 API 验证与生产环境变量配置单独记录完成证据；本地 mock 通过不等于 OpenRouter 链路已通过。

评估先用人工编写、双人复核的样本（每场至少 6 条典型输入，加相近主题、含糊与范围外输入），将一部分留作调词后的盲测。发布门槛以盲测的“人工可接受故事进入前二”及“第二项也讲得通”为主，记录分母和分歧案例；不得只凭模型 `confidence` 或个别演示样本决定上线。

本迭代的完成条件：用户输入问题后八面旋转，获得两张有效候选并能明确选其一；刷新、降级与返回修改均可用；最终故事、傩面、预载与得面结果一致；盲测样本显示两个候选对用户有可解释的意义。
